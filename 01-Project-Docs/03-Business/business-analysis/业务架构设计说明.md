# 互联网医疗平台业务架构设计说明文档

## 一、项目概述

### 1.1 项目定位
本系统是一个**综合性互联网医疗服务平台**，基于 **Vue3 + TypeScript + Vite + UniApp** 技术栈构建，支持多端部署（H5、微信小程序、支付宝小程序、APP等），为患者提供全场景、全周期的就医服务体验。

### 1.2 核心价值主张
- **便捷就医**：线上线下一体化，减少患者排队等待时间
- **全程陪伴**：从预约挂号到诊后随访的全流程服务
- **智能辅助**：AI预问诊、智能导诊、用药提醒等智能化服务
- **数据互通**：健康档案、检验检查报告等医疗数据的整合展示

## 三、核心业务域详解

### 3.1 挂号预约域（Registration Domain）

#### 业务场景
- **科室挂号**：按科室层级（一级/二级）选择预约
- **医生挂号**：查看医生排班、号源情况，进行预约挂号
- **云诊室**：线上视频/图文问诊
- **候补挂号**：号源紧张时的候补排队机制
- **特殊窗口**：警员专窗、人才专窗、院校专窗等定制化服务

#### 核心流程
```
患者选择科室/医生 → 查看号源排班 → 选择就诊时间 → 确认预约 → 支付挂号费 → 预约成功
```

#### 关键实体
- 科室（Department）
- 医生（Doctor）
- 排班（Schedule）
- 号源（Source）
- 预约订单（RegOrder）

---

### 3.2 预问诊域（Pre-Inquiry Domain）

#### 业务场景
- **AI预问诊**：智能对话收集病情信息
- **MDT预问诊**：多学科联合诊疗前的情况采集
- **专科问卷**：针对特定专科的标准化问卷（如妇科、儿科）
- **流调表**：疫情期间/特殊时期的流行病学调查

#### 核心价值
- 减少医生重复询问，提高诊疗效率
- 提前收集病情信息，辅助医生诊断
- 结构化病历数据，便于后续分析

#### 关键流程
```
患者进入预问诊 → 选择症状/回答问卷 → AI/系统分析 → 生成预问诊报告 → 同步给医生
```

---

### 3.3 健康档案域（Health Record Domain）

#### 业务场景
- **就诊史查询**：历次就诊记录、诊断信息
- **处方详情**：用药记录、药品信息
- **报告查询**：检验报告、检查报告、体检报告
- **病历档案**：门诊病历、住院病历、出院小结
- **电子发票**：医疗费用的电子票据

#### 数据整合逻辑
```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   HIS系统    │───→│   数据整合    │←───│   LIS系统    │
│  (临床数据)  │    │   中台服务    │    │  (检验数据)  │
└──────────────┘    └──────────────┘    └──────────────┘
                           ↓
                    ┌──────────────┐
                    │   患者端展示  │
                    │  (统一视图)   │
                    └──────────────┘
```

---

### 3.4 用药管理域（Medication Management Domain）

#### 业务场景
- **用药提醒**：根据医嘱自动生成用药提醒
- **用药计划**：长期用药的计划管理
- **药品查询**：药品说明书、库存查询
- **取药引导**：处方流转、取药地点指引

#### 业务规则
- 支持门诊处方、出院带药等多种用药来源
- 支持按频次（每日几次）、时间段（早中晚）设置提醒
- 支持用药打卡记录

---

### 3.5 智能陪诊域（Intelligent Escort Domain）

#### 业务场景
- **就诊流程引导**：当前环节提示、下一步指引
- **排队叫号**：实时排队进度、叫号提醒
- **院内导航**：科室位置、检查地点导航
- **电子导诊单**：就诊流程的可视化展示

#### 核心功能
```
就诊前：发送就诊提醒、交通建议
    ↓
就诊中：签到确认 → 候诊提醒 → 就诊引导 → 检查引导 → 取药引导
    ↓
就诊后：用药提醒 → 复诊提醒 → 随访提醒
```

---

### 3.6 慢病管理域（Chronic Disease Domain）

#### 业务场景
- **健康监测**：血压、血糖等生命体征的记录与跟踪
- **健康评分**：基于健康数据的综合评估
- **健康计划**：个性化的健康管理方案
- **饮食/运动建议**：生活方式干预指导

#### 支持病种
- 2型糖尿病
- 高血压
- 心血管疾病
- 肺部疾病
- 认知功能障碍

---

### 3.7 住院服务域（Inpatient Domain）

#### 业务场景
- **入院登记**：在线办理入院手续
- **住院管家**：住院期间的费用查询、每日清单
- **预交金缴纳**：住院押金的在线缴纳
- **院前检查**：入院前的检查预约
- **出生证明**：新生儿出生证明的预约办理

---

### 3.8 问卷随访域（Questionnaire Domain）

#### 业务场景
- **满意度调查**：门诊/住院满意度评价
- **诊后随访**：出院后随访、术后随访
- **专科评估**：如Kupperman评分、跌倒评估等
- **流调筛查**：传染病筛查、健康申报

#### 问卷类型
- 单选/多选题
- 填空题
- 量表评分题
- 图片上传题

---

### 3.9 便民服务域（Convenience Service Domain）

#### 业务场景
- **失物招领**：院内失物发布与认领
- **陪诊服务**：有偿/志愿者陪诊预约
- **非急救转运**：出院转运服务
- **服务电话**：医院各部门联系方式
- **停车引导**：院内及周边停车场信息

## 四、技术架构支撑

### 4.1 多端适配架构
```
┌─────────────────────────────────────────────────────────┐
│  统一代码库（UniApp + Vue3）                              │
├─────────────────────────────────────────────────────────┤
│  H5端    │   微信小程序   │   支付宝小程序   │   APP端   │
├─────────────────────────────────────────────────────────┤
│              条件编译 + 平台适配层                        │
└─────────────────────────────────────────────────────────┘
```

### 4.2 状态管理设计
- **Pinia Store**：
  - `userStore`：用户信息、就诊人管理
  - `globalStore`：全局配置、医院信息
  - `cacheStore`：缓存数据、临时状态
  - `medicationStore`：用药管理状态

### 4.3 接口架构
- **双版本兼容**：支持PHS 2.0和PHS 3.0接口
- **统一封装**：请求拦截、响应处理、错误处理
- **模块化组织**：按业务域划分API模块

## 五、后续优化方向

### 5.1 架构不足

| 序号 | 不足之处 | 具体表现 |
|------|----------|----------|
| 1 | **页面数量庞大，组织松散** | pagesA/B/C分包命名无明确业务含义，新成员难以快速定位 |
| 2 | **组件复用性不足** | 同类功能组件分散在各页面，如问卷组件重复开发 |
| 3 | **业务逻辑与视图耦合** | 部分页面业务逻辑复杂，未做有效的分层设计 |
| 4 | **配置化程度低** | 医院差异化需求需要硬编码修改，维护成本高 |
| 5 | **接口版本混乱** | 2.0和3.0接口混用，部分接口调用不规范 |
| 6 | **缺乏统一的数据字典** | 业务状态码、枚举值分散在各处 |
| 7 | **主题定制能力不足** | 中医院/西医院主题切换依赖条件判断，不够灵活 |

### 5.2 优化建议

#### 优化1：业务域驱动的目录重构
```
src/
├── domains/                    # 按业务域组织
│   ├── registration/           # 挂号预约域
│   │   ├── pages/              # 页面
│   │   ├── components/         # 组件
│   │   ├── composables/        # 组合式函数
│   │   └── api.ts              # 接口
│   ├── inquiry/                # 预问诊域
│   ├── health-record/          # 健康档案域
│   ├── medication/             # 用药管理域
│   └── ...
├── shared/                     # 共享资源
│   ├── components/             # 通用组件
│   ├── utils/                  # 工具函数
│   └── constants/              # 常量定义
└── platform/                   # 平台适配
    ├── h5/
    ├── mp-weixin/
    └── app/
```

#### 优化2：配置化业务规则引擎
- 提取医院差异化配置到JSON配置文件
- 支持表单字段、业务流程、UI主题的配置化
- 实现"零代码"适配新医院

#### 优化3：统一接口适配层
- 建立接口版本适配器，统一对外暴露标准接口
- 完善接口类型定义，提升TypeScript覆盖率
- 实现接口mock数据，支持离线开发

#### 优化4：问卷系统重构
- 设计通用问卷引擎，支持动态配置问卷
- 统一问卷组件，通过JSON Schema渲染
- 支持问卷模板复用

### 6.3 关键优化点总结

| 优化维度 | 当前状态 | 优化目标 |
|----------|----------|----------|
| **代码组织** | 按技术分层 | 按业务域组织 |
| **组件设计** | 分散重复 | 统一组件库 |
| **配置能力** | 硬编码为主 | 配置化驱动 |
| **接口管理** | 版本混杂 | 统一适配层 |
| **开发体验** | 维护困难 | 模块化、规范化 |
| **扩展能力** | 新医院接入成本高 | 低代码配置化 |

## 七、要点

### 7.1 当前能力展示
1. **功能完整性**：覆盖患者就医全流程，从预约到诊后随访
2. **多端覆盖**：一套代码支持H5、小程序、APP多端发布
3. **医院适配**：已服务多家医院，具备差异化适配能力
4. **扩展能力**：模块化设计支持功能快速扩展

### 7.2 待改进事项
1. **技术债务**：历史代码存在一定技术债务，需要逐步重构
2. **配置化程度**：当前配置化能力有限，部分需求需要开发介入
3. **性能优化**：部分页面加载性能有待优化

### 7.3 后续规划
1. **架构升级**：按业务域重构代码，提升可维护性
2. **配置化平台**：建设低代码配置平台，降低医院接入成本
3. **智能化升级**：引入AI能力，提升智能问诊、导诊体验
