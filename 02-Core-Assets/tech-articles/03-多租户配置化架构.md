# 多租户配置化架构设计 - 一套代码支持多医院

## 一、业务背景

医疗信息化项目中，一个产品需要卖给多家医院。每家医院有：
- 不同的品牌Logo、名称、配色
- 不同的功能开关（A医院要排队叫号，B医院不要）
- 不同的业务流程（预约是否要预付费）
- 不同的第三方集成（不同厂商的HIS系统）

**挑战**：如何一套代码支持所有医院，而不陷入 "if-else 地狱"？

### 3.3 组件级动态渲染

```javascript
// components/FeatureWrapper.jsx
import React from 'react';
import sysConfig from '@/utils/globleData';

/**
 * 功能开关包装器
 * @param {string} featureKey - 功能开关key
 * @param {ReactNode} children - 子组件
 */
export const FeatureWrapper = ({ featureKey, children, fallback = null }) => {
  const isEnabled = sysConfig[featureKey] === '1' || sysConfig[featureKey] === true;
  return isEnabled ? children : fallback;
};

// 使用示例
import { FeatureWrapper } from '@/components/FeatureWrapper';

const SomePage = () => {
  return (
    <div>

        <InternetHospitalCard />

};
```

### 4.1 配置继承与覆盖

```javascript
const defaultHospitalConfig = {
  isShowQueueNumber: false,

  isShowSatis: false,

  }),
```

### 4.2 配置校验

```javascript
// utils/configValidator.js

const requiredFields = [
  'sysCode',
  'hosId', 
  'title',
  'basePath',
  'logo',
];

const booleanFields = [
  'isShowQueueNumber',
  'isShowNetWork',
  'isShowSatis',
];

export const validateConfig = (config) => {
  const errors = [];
  
  // 必填字段校验
  requiredFields.forEach((field) => {
    if (!config[field]) {
      errors.push(`缺少必填字段: ${field}`);
    }
  });
  
  // 布尔值格式校验
  booleanFields.forEach((field) => {
    if (config[field] !== undefined) {
      const value = config[field];
      if (value !== true && value !== false && value !== '1' && value !== '0') {
        errors.push(`${field} 格式错误，应为布尔值或'1'/'0'`);
      }
    }
  });
  
  // basePath格式校验
  if (config.basePath && !config.basePath.startsWith('/')) {
    errors.push('basePath 必须以/开头');
  }
  
  if (errors.length > 0) {
    console.error('配置校验失败:', errors);
    throw new Error(`配置错误: ${errors.join(', ')}`);
  }
  
  return true;
};
```

### 4.3 打包脚本优化

```javascript
// scripts/build.js
const fs = require('fs');
const { execSync } = require('child_process');

const hospitals = [
  { sysCode: '1001033', name: 'taizhou' },
  { sysCode: '1001048', name: 'yixing' },
  { sysCode: '1001038', name: 'jiaer' },
];

// 批量打包所有医院
hospitals.forEach((hospital) => {
  console.log(`开始打包: ${hospital.name}`);
  
  // 修改配置文件
  const configPath = './src/utils/globleData.js';
  let content = fs.readFileSync(configPath, 'utf8');
  content = content.replace(
    /sysCode:\s*'\d+'/,
    `sysCode: '${hospital.sysCode}'`
  );
  fs.writeFileSync(configPath, content);
  
  // 执行打包
  execSync('umi build', { stdio: 'inherit' });
  
  // 重命名dist目录
  fs.renameSync('./dist', `./dist-${hospital.name}`);
  
  console.log(`打包完成: ${hospital.name}`);
});
```

## 五、与其他架构模式对比

| 方案 | 优点 | 缺点 | 适用场景 |
|-----|------|------|---------|
| **本方案（配置驱动）** | 一套代码，维护简单 | 配置复杂度高 | 功能差异大但核心流程相同的SaaS产品 |
| 分支开发 | 完全隔离，风险低 | 代码冗余，合并困难 | 差异极大的定制化项目 |
| 插件化架构 | 扩展性强 | 架构复杂，学习成本高 | 需要第三方扩展的平台型产品 |
| 微前端 | 技术栈无关 | 部署复杂，通信成本高 | 多团队独立开发的大型项目 |

## 六、踩坑记录

### 坑1：配置缓存问题

**现象**：修改配置后页面没变化
**原因**：Webpack打包时缓存了配置
**解决**：
```javascript
// 配置改为动态读取
const getConfig = () => {
  // 每次重新require，避免缓存
  delete require.cache[require.resolve('./globleData')];
  return require('./globleData');
};
```

### 坑2：TypeScript类型提示

**现象**：配置项没有类型提示
**解决**：
```typescript
// types/hospital.d.ts
export interface HospitalConfig {
  sysCode: string;
  hosId: string;
  title: string;
  logo: string;
  basePath: string;
  isShowQueueNumber?: boolean;
  isShowNetWork?: boolean;
  // ...其他字段

declare module '@/utils/globleData' {
  const config: HospitalConfig;
  export default config;

```

### 坑3：静态资源路径

**现象**：打包后图片404
**原因**：basePath变化导致资源路径错误
**解决**：
```javascript
// 使用相对路径或动态计算

// 或在webpack中配置publicPath
output: {
  publicPath: sysConfig.basePath,
}
```

## 七、面试话术

**Q: 你们一套代码是怎么支持多家医院的？**

> "我们采用的是**配置驱动架构**。核心思想是：
> 
> 1. **配置中心**：维护一个医院配置表，每家医院的差异化需求（Logo、功能开关、业务流程）都抽象为配置项
> 2. **动态渲染**：组件根据配置决定是否渲染，而不是写死if-else
> 3. **动态路由**：Umi路由的hideInMenu属性根据配置动态控制
> 4. **动态打包**：修改一个sysCode变量，即可打包出不同医院的部署包
>
> 比如排队叫号功能，A医院要B医院不要。我们在配置里定义`isShowQueueNumber`，组件用FeatureWrapper包裹，自动根据配置显示隐藏。这样既保证了代码复用，又满足了个性化需求。"

**Q: 如果医院之间差异很大怎么办？**

> "确实有这种情况。我们的策略是：
> 1. **核心流程复用**：预约挂号、报告查询这些通用流程一套代码
> 2. **差异点配置化**：通过配置控制功能开关和业务流程
> 3. **极端情况插槽**：实在无法配置的，用组件插槽让医院自定义
> 
> 目前我们一套代码支持了8家医院，代码复用率超过90%。"
